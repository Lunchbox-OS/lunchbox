# v0.6.0, sealed empty by release immutability (#203)

## Prompt

> check the logs again -- looks like I have something set up wrong in the
> repository settings
>
> don't delete the tag -- looks like the config deploy succeeded, but do the
> rest all on the same branch

The first tag-driven release after #223 merged: run 35998288355, on
`v0.6.0`.

## What happened

| Time (UTC) | Event |
|---|---|
| 11:13:30 | A `v0.6.0` release was created in the GitHub UI, as a draft, with no assets |
| 12:19:02 | The draft was published. That created the tag (lightweight, not `git tag -a`) |
| 12:19:05 | The tag push started `release.yml` |
| 12:46 | `publish`, attempt 1: signing and attestation passed, then `Release v0.6.0 is already published; adding any missing assets` → `HTTP 422: Cannot upload assets to an immutable release` |
| later | attempt 2: the same |

The repository has **release immutability** on. GitHub's documentation:

> Once an immutable release is published, its associated Git tag is locked to
> a specific commit, cannot be changed, and cannot be deleted while the release
> exists. … If you delete the immutable release, you can delete the tag, but
> you cannot reuse the same tag name.

So publishing the empty draft sealed it, and `v0.6.0` can never carry a
release with packages. `release.yml` already does what the same documentation
recommends: draft, attach every asset, then publish. That only works if the
workflow is what creates the release.

Immutability itself is right for this project, and stays on. Note 005 already
treats release assets as load-bearing: the apt index points at them, and a
changed asset breaks installs of that version against an index that still
verifies.

Nothing else was lost. Signing succeeded on both attempts, which is the first
real evidence that the `release` environment's subkey matches
`dist/apt/repository.key`. The apt site was never touched. The config editor
deploy, which had failed earlier because the Pages project did not exist yet,
succeeded once it did.

## What changed

* **`check-release-tag.sh`**, run by the guard job before anything builds. It
  refuses a tag whose release is published by anyone but
  `github-actions[bot]`, which is the login GitHub records for releases made
  with `GITHUB_TOKEN`, checked against `cli/cli` and `rhysd/actionlint`. A
  draft passes, and so does a release the workflow published itself (a re-run
  after a later step failed).
* **`publish-release.sh`** no longer tries to add missing assets to a
  published release, which immutability forbids. It accepts a published
  release only if every asset is already there, and otherwise says the tag
  is burned.
* **Docs:** a "Cutting a release" section in `docs/release-signing.md`, and a
  warning in `release.yml`'s header.
* **`404.html` in the apt site.** Before the release, the `lunchbox-apt`
  placeholder had no `404.html`, so Pages served it as a single-page app and
  answered `dists/stable/InRelease` with a 200. The first publish would have
  taken it for an index. The placeholder was redeployed with one. The real
  site now ships its own, so this never depends on Pages' fallback again, and
  the runbook tells the next person setting up a placeholder.
* **0.6.1**, since `v0.6.0` cannot be reused.

Both scripts were run against the real `v0.6.0`, read-only in the paths
exercised: `check-release-tag.sh` refuses it and passes `v0.6.1`, and
`publish-release.sh` names the missing files and exits without uploading.

## Left as it is

The empty `v0.6.0` release and its tag. The tag stays at the user's request,
and it cannot be deleted while the release exists. The release is currently
GitHub's "Latest". `gh release create` picks Latest by date and version
unless told otherwise, so 0.6.1 should take that over.
