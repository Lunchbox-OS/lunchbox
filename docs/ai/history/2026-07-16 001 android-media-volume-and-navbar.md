## 1. Media volume

**Symptom.** Video playback in Khan was quiet even at full host volume.

**Root cause.** Android's per-stream volume sits *before* the host PulseAudio sink
shepherd controls. `STREAM_MUSIC` (the media stream) defaults to `5/15` (~33 %), so
media was attenuated to a third before shepherd's own volume ever applied — the
shepherd slider only ever spanned the bottom third of the real range.

**Fix.** Max `STREAM_MUSIC` at each launch so shepherd's host volume owns the full
range. New helper action `max-volume`.

Findings that shaped it:

- The `media` CLI (`media volume …`) is **absent** on this LineageOS 13 image;
  `cmd audio` only exposes surround-format commands. The working setter is
  `cmd media_session volume --stream 3 --set N`.
- `waydroid shell cmd …` eats a forwarded `--stream`/`--set`/`--get` as its *own*
  flags — must be `waydroid shell -- cmd …` (same `shell --` trick as `pin`/`unlock`).
- `--set INDEX` **rejects** an out-of-range index (does not clamp), and the max is
  ROM-specific (`[0..15]` here, `[0..25]` on some ROMs). So `max-volume` is a
  two-step (query) action like `maximize`: read the max from `--get`'s
  `volume is <cur> in range [0..<max>]`, then `--set` it.
- Applied per launch (after the window is ready, all lock modes — media plays in
  locktask too); the setting can drift within a session.

## 2. Hiding the nav bar

**Goal.** In the kiosk the Android software nav bar is redundant: the HUD surfaces
Back, and lock-down disables home/recents/search — so the bar only ever shows Back
(or nothing).

**What did NOT work.**

- `settings put global policy_control immersive.*` — the `policy_control`
  mechanism was **removed in Android 11+**; on this Android 13 image it's a no-op
  (`immersive.full=*` was already set and the nav bar stayed `isVisible=true`).
- `settings put system volume_music` — legacy, ignored by the modern AudioService.

**What works: `qemu.hw.mainkeys=1`.** Makes Android treat the device as having
hardware nav keys, so SystemUI draws no software nav bar at all
(`dumpsys window` → 0 `NavigationBar0` windows).

Applying it correctly took some digging into Waydroid's prop pipeline:

- `waydroid prop set` only persists `persist.*` props (stored in Android's
  persistent-property store inside userdata). `qemu.hw.mainkeys` is not `persist.*`,
  so setting it at runtime is wiped on the next restart — and it's read at boot
  anyway (too late).
- The boot-time prop set is generated by `make_base_props` into
  `waydroid_base.prop`, which `make_prop` reads at each container start. But
  `make_base_props` runs **only on `waydroid init`/`upgrade`**, not on session
  start — so cfg `[properties]` alone doesn't take effect until a regen.
- Canonical apply: record the prop in `waydroid.cfg`'s `[properties]` (durable
  across future upgrades) **and** run `waydroid upgrade -o` (offline: no image
  download; regenerates `waydroid_base.prop`; restarts the container).

**Where it lives.** New `configure_waydroid_navbar` in `scripts/lib/waydroid.sh`,
called from the `apps install android` flow after `install_libndk`. Idempotent on
the baked `waydroid_base.prop`, so the second install pass (which provisions the
DPC against a *running* session) is a no-op and won't restart the container out
from under that session.

## Validation

- Helper `max-volume`: live `4 → 15`, and via shepherd's exact
  `pkexec /usr/libexec/shepherd-waydroid-helper max-volume` call (non-interactive
  as the daemon user) `3 → 15`. 17 helper unit tests pass (`parse_volume_max` +
  fixed-command). The auto-fire on a shepherd launch couldn't be observed in the
  headless harness this run — Waydroid's window didn't map without a GPU ("did not
  present a window within 45s"), which is upstream of the `max_volume` call — but
  the pkexec path and placement are otherwise proven.
- Nav bar: `qemu.hw.mainkeys=1` via cfg `[properties]` + `waydroid upgrade -o` →
  `getprop qemu.hw.mainkeys` = 1, 0 `NavigationBar0` windows after a session start.
