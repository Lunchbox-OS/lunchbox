# F-Droid repository for the Android apps (#110)

## Prompt

> `/remote-control` — scope out
> [#110](https://git.armeafamily.com/albert/shepherd-launcher/issues/110).

> **Publish F-Droid repository for shepherd-media-android and shepherd-companion**
>
> Android installations are currently accomplished by manually downloading and
> installing the APKs. There is no auto-update mechanism along the lines of the
> APT repository for the .deb.
>
> Let's add a F-Droid repository for these shepherd-media-android and
> shepherd-companion. My understanding is that these are basically static sites,
> so even pushing files to a GitHub Pages site will work.
>
> Geofencing (along the lines of what is done for the source code and APT
> repositories) is out of scope for this ticket, as shepherd-companion and
> shepherd-media-android have very limited utility without shepherd-launcher.

Scoping only (no implementation in this pass). This is the Android sibling of
[`2026-07-19 002 forgejo-apt-repository.md`](2026-07-19%20002%20forgejo-apt-repository.md).

## Where we are today

`release.yml`'s `apk` matrix builds one signed release APK per Android module and
attaches it to the Forgejo release with a `.sha256` sidecar:

| Asset (v0.3.0) | Size |
|---|---|
| `shepherd-companion_0.3.0.apk` | 46.5 MB |
| `shepherd-media_0.3.0.apk` | 65.8 MB |

Installation is a manual download + `adb install` (`docs/INSTALL.md:97`). There
is no update path at all — the phone never learns a new version exists.

**The two hard prerequisites for an F-Droid repo are already satisfied**, which
is most of why this is a small ticket:

1. **A stable signing key.** Both modules sign with the same CI keystore
   (`SHEPHERD_KEYSTORE_B64` + friends), and F-Droid keys an app's update chain
   off its signing certificate.
2. **A monotonic `versionCode`.** Both `build.gradle.kts` files derive it from
   the root `VERSION` as `major*10000 + minor*100 + patch` (0.3.0 → 300), and
   `applicationId`s are stable (`com.armeafamily.shepherd.companion`,
   `com.armeafamily.shepherd.media`).

## What an F-Droid repo actually is

The issue's read is right: it is a directory of static files served over HTTPS.

```
<base>/entry.jar          signed pointer at the index (what the client fetches first)
<base>/entry.json
<base>/index-v2.json      the actual catalogue
<base>/index-v1.jar       legacy index, for clients older than ~2023
<base>/com.armeafamily.shepherd.companion_300.apk
<base>/icons-640/…        app icons — a SUBDIRECTORY (see Finding 4)
```

Generated by `fdroidserver`'s `fdroid update`, which signs the index with a
keystore. The client adds the repo as `<base>?fingerprint=<sha256 of that key>`.

The important structural difference from the apt work: **Forgejo has no F-Droid
package registry** (its registry list is Debian, RPM, Alpine, Cargo, generic, …),
so unlike the `.deb` case — where Forgejo generates and signs the index for us —
here *we* generate the index, *we* sign it, and *we* pick a host.

## Findings

**1. `fdroidserver` is packaged in Ubuntu 26.04.** `apt-cache policy fdroidserver`
→ `2.4.3-1` from `resolute/universe`. It pulls `androguard` (APK parsing — no
`aapt` needed since fdroidserver 2.x), `apksigner`, and a JDK. The android CI
image already carries the JDK + SDK, so this is one line in
`.ci/Dockerfile.android` (or a job-time `apt-get install`, at ~30 s per run).
No vendoring, no pip, no Docker image from a third party.

**2. The index needs its own signing key, and its fingerprint is permanent.**
The repo URL every device is configured with embeds the fingerprint. Lose or
rotate the key and every device must remove and re-add the repo. Cheapest option
that avoids a second secret to manage: add a **new alias** to the existing
release keystore (`keytool -genkeypair -keystore shepherd-release.jks -alias
fdroid-index`), re-base64 it into `SHEPHERD_KEYSTORE_B64`, and add a
`SHEPHERD_FDROID_ALIAS` secret. Reusing the *app* alias also works and needs no
secret changes at all, but then one key compromise burns both the apps and the
repo. Either way: back the keystore up somewhere that survives the CI secret.

**3. `fdroid update` rebuilds the index from whatever is sitting in `repo/`.**
That makes the repo *stateful* — to keep old versions listed, CI would have to
reconstitute every previously published APK before each run. Recommendation:
**publish only the current version of each app.** Then the job is stateless (two
APKs in, a repo out), the published set is ~112 MB regardless of release count,
and the only thing users lose is the ability to downgrade from within F-Droid —
every historical APK is still on its Forgejo release. If an archive is ever
wanted, the natural upgrade is to `curl` the last N releases' APKs into `repo/`
before running `fdroid update`.

**4. Flat-namespace hosts cost us icons.** Forgejo's generic registry restricts
filenames to `[a-zA-Z0-9.+_-]` — no slashes, so no `icons-640/` — and release
assets are likewise a flat namespace. `fdroid update` writes extracted launcher
icons into `repo/icons-<dpi>/`, so under a flat host those references 404 and the
client shows placeholder icons. Functionally harmless, cosmetically obvious. Only
the "real static directory" options (C/D below) avoid it.

**5. "Auto-update" means something weaker on Android than `apt upgrade`.**
F-Droid ≥ 1.19 does do fully unattended background updates on Android 12+, but
**only for apps F-Droid itself installed** (it uses the installer-session API,
which requires being the installer of record). Practical consequences:

- **companion** (`minSdk 31`, phones) — the good case. Existing sideloaded
  installs are recognised because the signature matches; the *first* update
  through F-Droid prompts, and after that F-Droid is the installer of record and
  updates land silently.
- **media** — targets Fire TV sticks (Fire OS 7/8 ≈ Android 9/11, hence
  `minSdk 24` and the armeabi-v7a ABI). Below Android 12 there is no unattended
  path without root, and F-Droid has no leanback/D-pad UI, so on the sticks this
  stays a manual, remote-driven chore and `adb install` remains the sane path.

So the ticket's value is concentrated in companion. Still worth publishing media
(it costs one extra metadata file, and any phone/tablet running it benefits), but
the sticks should not be expected to self-update.

**6. Geofencing is out of scope but the host choice decides whether it is ever
possible.** Options A–C sit behind the same nginx that already fronts
`git.armeafamily.com` and inherit whatever policy is applied there; GitHub Pages
(D) permanently cannot be geofenced.

## Hosting options

| | Base URL | Icons | New infra | Notes |
|---|---|---|---|---|
| **A. Forgejo generic registry** *(recommended)* | `…/api/packages/albert/generic/fdroid/repo/` | ✗ | none | Per-file `PUT`/`DELETE`; reuses the `PACKAGE_TOKEN` (`write:package`) already minted for apt. |
| **B. A dedicated `fdroid` release** | `…/releases/download/fdroid/` | ✗ | none | Verified live: serves 200 directly (no redirect), with `ETag`/`Last-Modified`/range support. But Forgejo allows *duplicate* asset names in one release (v0.2.2 has two `…amd64.deb` assets), so publishing must delete by asset id first — and it clutters the releases list. |

Because the generator runs inside that stack it reads Forgejo over the internal network — no credentials, and `release.yml` is untouched. |
| **D. GitHub Pages** (the issue's suggestion) | `https://<user>.github.io/…` | ✓ | a GitHub repo + deploy token | Mirrors ~112 MB/release off-site, adds an external dependency, never geofenceable, and Pages' ~1 GB site soft limit becomes a real ceiling if an archive is kept. |

**Recommendation: C**, worked out in detail in
[Appendix: option C](#appendix-option-c--static-repo-on-the-forgejo-host) below.

**A** mirrors the apt decision — zero new infrastructure, reusing the token and
script shape already in the tree — and it is the right answer if the goal is "no
server-side state, ever". But once the actual deployment is on the table (the
[`fahrengit-451`](https://github.com/aarmea/fahrengit-451) compose stack, with the
Actions runner in the homelab), C stops being the expensive option: the repo
generator becomes a service *inside* that stack reading Forgejo over the internal
bridge network, so it needs no credentials, no CI secret, and no change to
`release.yml` at all — while still buying real icons, screenshots, an installable
archive, and a QR-code landing page.

Switching hosts later is a base-URL change: the fingerprint survives (same key),
but every device must re-add the repo — for a handful of family devices, one QR
scan each.

Two things to confirm before committing to A (each ~2 minutes with a token):

- generic-registry downloads are public for a public owner (the Debian registry
  is, so this is very likely);
- no per-file size cap below 66 MB (`[packages] LIMIT_SIZE_GENERIC`).

## Design (assuming A — see appendix §8 for what drops out under C)

Mirrors the `.deb` split — a `shepherd` subcommand builds the artifact locally,
a `scripts/ci/` script publishes it.

### 1. Checked-in metadata — `dist/fdroid/`

```
dist/fdroid/config.yml                                   # template, ${…} for repo_url/keystore
dist/fdroid/metadata/com.armeafamily.shepherd.companion.yml
dist/fdroid/metadata/com.armeafamily.shepherd.media.yml
```

Each metadata file carries `Name`, `Summary`, `Description`, `License`,
`AuthorName`, `WebSite`, `SourceCode`, `Categories`. Deliberately **no version
fields** — `fdroid update` reads `versionCode`/`versionName` out of the APK, so
`VERSION` stays the single source of truth and `shepherd version check` gains
nothing to police.

### 2. `shepherd package fdroid` (`scripts/lib/package.sh`)

Takes the built APKs (`dist/pkg/*.apk`), stages `repo/`, materialises
`config.yml` from the template + env, runs `fdroid update --pretty
--delete-unknown`, leaves a ready-to-serve tree in `dist/fdroid-repo/`. Runnable
locally with a throwaway keystore, which is what makes the whole thing testable
without CI.

### 3. `scripts/ci/publish-fdroid.sh`

Sibling to `publish-apt.sh`: for each generated file, `DELETE` then `PUT` to
`…/api/packages/${OWNER}/generic/fdroid/repo/<filename>` (409-tolerant, same
error-surfacing shape). Also deletes the previous release's APK filenames, since
"current version only" means the old `…_290.apk` should stop being served.

### 4. `release.yml` — a new `fdroid` job

The wrinkle: **Forgejo has no cross-job artifacts** (see the header comment in
`release.yml`), so a job downstream of the `apk` matrix cannot receive the APKs.
Cleanest workaround, and arguably a feature: `needs: [apk]`, then download the
two APKs the matrix just attached, straight from the release by tag:

```
GET {server}/{repo}/releases/download/{tag}/shepherd-{companion,media}_{version}.apk
```

That also makes the job re-runnable on its own for an already-published tag.
Gating matches apt: skip on dry runs (no release exists to pull from) and skip
prereleases (`!contains(github.ref_name, '-')`).

### 5. Docs

- `docs/INSTALL.md` — an "Installing the Android apps from F-Droid" section: add
  the repo (URL + fingerprint, ideally a QR code — `fdroidserver` depends on
  `python3-qrcode` and can emit one), then install; keep `adb install` as the
  manual/Fire TV path; state plainly which devices self-update (Finding 5).
- `companion-android/README.md`, `crates/shepherd-media-android/README.md` — one
  line each pointing at the INSTALL section.

## Effort

Small-to-medium; roughly a day, no new toolchain to invent.

- Metadata + config template — ~1 h (mostly writing the two app descriptions).
- `shepherd package fdroid` + `publish-fdroid.sh`, shellcheck-clean — ~3 h.
- `release.yml` job + APK-download helper — ~1 h.
- Docs — ~1 h.
- One-time, outside code: index key alias, keystore secret refresh, first publish
  via `workflow_dispatch`, then add the repo on a phone and watch a real
  0.3.0 → 0.3.1 update land — ~1 h.

## Decisions needed

1. **Host** — C (recommended, see appendix), A, B, or D.
2. **Index key** — under C the key is a file on the droplet rather than a CI
   secret, so "new alias in the existing keystore" matters less; a purpose-made
   keystore for the index is just as cheap. Either way: back it up off-box.
3. **History** — C makes `archive_older: 3` available, which dissolves this
   question; under A/B it is current-version-only.
4. **Media in the repo?** — recommended yes, with the Fire TV caveat documented.
5. **Free space on the droplet** — the one hard blocker I cannot check from here
   (see appendix §6).

## Risks

- **Fingerprint permanence** — losing the index key means re-adding the repo on
  every device. Back the keystore up off-CI.
- **Placeholder icons** under A/B (Finding 4).
- **Unverified**: generic-registry public read + any generic size limit (above).
- **Expectation gap**: the issue asks for "an auto-update mechanism along the
  lines of the APT repository". On phones that lands; on the Fire TV sticks it
  does not, and the docs should say so rather than imply parity.

# Appendix: option C — static repo on the Forgejo host

## 0. What the host is

`git.armeafamily.com` → `137.184.100.208` (DigitalOcean VPS), running the
[`aarmea/fahrengit-451`](https://github.com/aarmea/fahrengit-451) stack: a
five-service Docker Compose deployment of Forgejo behind a **containerized**
nginx 1.27.4 built with `ngx_http_geoip2_module`, plus `geoipupdate`,
`geoblock_watcher`, and certbot. The Actions runner is in the homelab, i.e. on
the other side of the internet from this box.

Four properties of that stack drive everything below:

1. **nginx's `conf.d` is deliberately not host-mounted.** The vhost is
   `nginx/templates/git.conf.template`, `COPY`d into the image and rendered by
   the nginx entrypoint's `envsubst` at container start. So adding a static
   `location` is an edit to *that repo*, followed by
   `docker compose up -d --build nginx` — not a file drop on the server.
2. **Geo-blocking is per-URL-path, not server-wide.** `geoblock_watcher` reads
   `config/geo_rules.yml` and renders one `location ^~ <path>` per entry into
   `geoblock/repo_locations.conf`, which the vhost `include`s *above* the
   catch-all `location /`. Nothing is blocked by default. (This corrects the
   guess in the options table above: a new `/fdroid/` location inherits **no**
   geofence — which is exactly what the issue asks for — but see §5 for the
   collision this creates if a rule is ever added.)
3. **The stack is deliberately SSH-free.** `FORGEJO__server__DISABLE_SSH=true`;
   git is HTTPS-only precisely so that everything is geofenceable at the HTTP
   layer. An inbound rsync-over-ssh deploy path cuts directly against that
   design.
4. **Security headers are `add_header … always` at `server{}` level** —
   `Strict-Transport-Security`, `X-Frame-Options`, `X-Content-Type-Options`,
   `Referrer-Policy`. This makes the `add_header` inheritance trap in §2 a real,
   specific hazard rather than a theoretical one.

Worth noting up front: **the 46 MB + 66 MB APKs already stream off this box** on
every release download today. So option C adds no new class of egress, and the
"but GitHub Pages is a CDN" argument for D is weaker than it sounds — the same
droplet is already the origin.

## 1. URL shape

`fdroidserver` requires `repo_url` to end in `/repo`. Two shapes:

- **Path on the existing vhost — `https://git.armeafamily.com/fdroid/repo`**
  (recommended). Existing certificate, existing server-level config, one
  `location` block. Forgejo routes `/{user}/…` from the same vhost, so declare it
  as `location ^~ /fdroid/` — the `^~` prefix wins over both the proxy catch-all
  and any regex location, and shadows only a hypothetical Forgejo user named
  `fdroid`.
- **Subdomain — `https://fdroid.armeafamily.com/repo`.** Cleaner separation and
  independent caching/geo policy, at the cost of a DNS record, a certbot entry,
  and a second copy of the server config. Only worth it if the policies are meant
  to diverge.

## 2. The nginx change (in fahrengit-451)

Two files in that repo, plus a volume:

```nginx
# nginx/nginx.conf, http{} level, next to the existing maps.
# Index files change every release; an APK at a given versionCode never does.
map $uri $fdroid_cache {
    ~\.apk$  "public, max-age=31536000, immutable";
    default  "no-cache";
}
```

```nginx
# nginx/templates/git.conf.template, inside the 443 server{}, ABOVE `location /`
location ^~ /fdroid/ {
    alias /srv/fdroid/;            # trailing slash on BOTH sides
    autoindex off;
    gzip off;                      # .apk/.jar are already deflated

    # add_header does NOT merge — see below.
    add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;
    add_header X-Frame-Options            SAMEORIGIN                            always;
    add_header X-Content-Type-Options     nosniff                               always;
    add_header Referrer-Policy            strict-origin-when-cross-origin       always;
    add_header Cache-Control              $fdroid_cache                         always;
}
```

```yaml
# docker-compose.yml — nginx service
volumes:
  - fdroid_repo:/srv/fdroid:ro
```

Two traps worth knowing before someone hand-writes this:

- **`add_header` does not merge.** Declaring *any* `add_header` in a `location`
  discards every one inherited from `server{}`. This stack sets four security
  headers there, so a naive one-line cache header would silently drop HSTS and
  friends for all F-Droid paths — hence the re-declaration above. (The
  alternative is moving all five to `http{}` level, which touches more of the
  existing config.)
- **Nested `location` blocks** inside the `alias` block would reproduce the same
  problem one level deeper, which is why the cache policy is a `map` rather than
  two nested regex locations.

Because `conf.d` is baked into the image (§0), applying this is
`docker compose up -d --build nginx` — a ~2 minute rebuild of the GeoIP2 module
layer, not a hot reload. Worth knowing that it is not in the watcher's
zero-downtime path.

Nothing else is needed: nginx's stock `mime.types` already maps `.apk` →
`application/vnd.android.package-archive` and `.jar` → `application/java-archive`,
and static serving gives Range requests plus `ETag`/`If-Modified-Since` for free
— which is the quiet win here, since the client re-checks the index on every scan
and a 66 MB APK over phone wifi wants to be resumable.

## 3. Getting the files there

With the runner in the homelab and the stack SSH-free, this is no longer a close
call: **C2 (the server generates the repo) wins, and it wins bigger than it did
in the abstract** — because the generator can live *inside the compose stack* and
fetch from `http://forgejo:3000` over the internal bridge network. No TLS, no
geoblock, no public egress, no credentials, and the "download the APKs" step is
effectively a local copy of files that are already on the same disk.

### C2 — an `fdroid` service in the compose stack *(recommended)*

```yaml
# docker-compose.yml
  fdroid:
    build: ./fdroid
    container_name: fdroid
    restart: unless-stopped
    environment:
      - FDROID_SOURCE=albert/shepherd-launcher   # or a list, see below
      - FDROID_REPO_URL=https://${DOMAIN}/fdroid/repo
      - FDROID_KEYSTOREPASS=${FDROID_KEYSTOREPASS}
      - FDROID_KEYPASS=${FDROID_KEYPASS}
    volumes:
      - ./config/fdroid-keystore.jks:/keystore.jks:ro
      - fdroid_repo:/srv/fdroid                  # rw here, :ro in nginx
    networks:
      - internal
    depends_on:
      - forgejo

volumes:
  fdroid_repo:
```

The loop, every N minutes:

1. `GET http://forgejo:3000/api/v1/repos/${FDROID_SOURCE}/releases/latest`;
2. bail unless the tag changed since the last run (state file in the volume);
3. skip prereleases (`"prerelease": true` in that same JSON — cleaner than the
   `contains(ref_name, '-')` string test `release.yml` uses for apt);
4. `git clone --depth 1 --branch <tag> http://forgejo:3000/${FDROID_SOURCE}` and
   take `dist/fdroid/` from it — so the app metadata, descriptions, and icons stay
   **versioned in shepherd-launcher**, tied to the exact tag being published;
5. download the release's `*.apk` assets into `repo/`;
6. `fdroid update`, then the atomic swap from §4.

What this buys, concretely: **no deploy key, no CI secret, no inbound SSH, and
`release.yml` is untouched.** The entire shepherd-launcher side of this ticket
collapses to metadata files, a local-testing subcommand, and docs. Publishing
also becomes independently re-runnable (`docker compose restart fdroid`) without
re-running a release.

Design notes worth settling before writing it:

- **Where the service lives.** It belongs in fahrengit-451, next to
  `geoblock_watcher`, which is the same shape: a small Python container watching
  a config file and rendering output for nginx. Follow that precedent and make it
  **config-driven** (`config/fdroid.yml` listing source repos + appids) rather
  than hardcoding shepherd, so the deployment repo stays a general git-host stack
  and the shepherd specifics stay in shepherd-launcher.
- **The image.** There is an official
  `registry.gitlab.com/fdroid/docker-executable-fdroidserver`, but it is an
  "executable image" meant for `docker run --rm -v $(pwd):/repo`, and it does not
  bundle the Android SDK. For a long-running service, a ~15-line Dockerfile on
  `debian:trixie-slim` with `fdroidserver` + `default-jdk-headless` + `apksigner`
  from apt is more predictable, pins cleanly, and matches how `geoblock_watcher`
  and `nginx` are already built in this stack. (fdroidserver 2.4.3 is in
  Debian/Ubuntu; APK parsing is androguard, so no SDK is needed — only a JDK and
  apksigner for signing the index.)
- **The keystore** is a bind-mounted file with passwords in `.env`, matching how
  `MAXMIND_LICENSE_KEY` is already handled. It is the one piece of state on the
  box that is not regenerable — back it up off-box (§6).
- **Poll interval.** 15 minutes is plenty; the loop is one cheap internal HTTP
  request when nothing has changed. A webhook would be tighter but adds an
  inbound endpoint for no real benefit at this cadence.

### C1 — push from CI (`fdroid deploy`), for contrast

`fdroid deploy` publishes over **rsync-over-ssh**, driven by one config key:

```yaml
serverwebroot: fdroid-deploy@git.armeafamily.com:/srv/fdroid/
```

Server side, the hardened shape is a dedicated unprivileged user whose key can do
nothing but write that one tree:

```
# ~fdroid-deploy/.ssh/authorized_keys
restrict,command="rrsync -wo /srv/fdroid" ssh-ed25519 AAAA… ci@shepherd
```

(`rrsync` ships with rsync; `-wo` = write-only, so the key cannot read anything
back.) CI gains one secret, `FDROID_DEPLOY_KEY`.

Three reasons this is the wrong shape *for this deployment* specifically:

- It puts a credential on a homelab runner that can write into a directory on the
  VPS hosting Forgejo — strictly more blast radius than option A's scoped
  `write:package` token, and unlike A it is not confined to a package namespace.
- It requires exposing host SSH to the homelab on a box whose stack disables
  Forgejo SSH on purpose (§0.3), so that every access path stays HTTP and stays
  geofenceable. Adding an SSH ingress is a policy reversal, not a config tweak.
- It still owes the `release.yml` wrinkle: no cross-job artifacts on Forgejo, so
  the `fdroid` job has to pull the APKs back out of the release the `apk` matrix
  just published.

The one thing C1 has over C2 is where the index signing key lives: a CI secret in
Forgejo's encrypted store, rather than a file on the droplet. That is a real but
narrow advantage — the *app* signing keystore already lives on this same machine
inside Forgejo's secrets, so C2 does not move the key to a new machine, it weakens
its at-rest posture on a machine that already holds one. Not worth an SSH ingress.

### The trade C2 does make

State that lives on the server and not in git: the keystore, the last-published
tag, and the compose/nginx changes. The last is mitigated by fahrengit-451 being a
real versioned repo — the service, its Dockerfile, the volume, and the nginx
location all land there as a reviewable diff, not as an undocumented change on a
box. The keystore is the genuine exception, and §6 says what to do about it.

## 4. Atomic publish

`fdroid update` writing in place leaves a window where the index advertises an APK
that hasn't finished landing — and nginx is serving that same directory out of the
shared volume the whole time. Build into a versioned directory and swap a symlink
instead:

```sh
# fdroid update runs against /srv/fdroid/repo-0.3.1/
ln -sfn repo-0.3.1 /srv/fdroid/.repo.tmp
mv -T /srv/fdroid/.repo.tmp /srv/fdroid/repo     # atomic rename
ls -dt /srv/fdroid/repo-* | tail -n +4 | xargs -r rm -rf
```

`mv -T` over a symlink is an atomic `rename(2)`, nginx follows symlinks by default
(`disable_symlinks off`) and `open_file_cache` is off by default, so there is no
stale-descriptor window. Rollback becomes re-pointing the symlink, and the
last-three-versions prune is one line. (`rsync --delay-updates` is *not* enough on
its own — the ordering constraint is specifically that the index must land last.)

## 5. What C buys that A and B cannot

This is the actual case for spending the extra effort:

- **Icons.** `repo/icons-<dpi>/` is a subdirectory, which flat hosts can't express
  — under A/B every app shows a placeholder.
- **Screenshots and rich listings** via `metadata/<appid>/en-US/phoneScreenshots/`.
  `docs/readme/` already has capture material, though those are launcher shots —
  companion/media shots would need capturing on-device, for which the adb setup
  from the BLE on-device testing notes is already in place (`adb exec-out screencap`).
- **A real archive.** `archive_older: 3` emits an `archive/` subdirectory so older
  versions stay installable and downgradeable from inside the client. Impossible
  on a flat host, and it dissolves Finding 3's "current version only" compromise.
- **A landing page** at `/fdroid/` with the repo URL and a QR code, so onboarding a
  new phone is "scan this" instead of "type this 64-hex fingerprint".
- **Range + conditional GET** straight from nginx (§2).
- **Geofencing stays available** — `geo_rules.yml` is keyed on a URL path prefix
  and rendered as a generic `location ^~ <path>`, not on anything Forgejo-specific,
  so `- path: /fdroid` would Just Work on a static tree. Out of scope per the
  issue, and correctly *off* by default (§0.2) — but see the collision below
  before assuming it can be switched on later for free.

### The one interaction to get right: prefix collision with the geo-blocker

`geoblock_watcher` renders `location ^~ /fdroid` (it `rstrip("/")`s the configured
path); the static tree needs `location ^~ /fdroid/`. Among prefix locations nginx
picks the **longest match**, so the static block would win for every path under
`/fdroid/` and the geo-block location would only ever catch the bare `/fdroid`.
A rule added later would appear to be configured and silently do nothing.

This costs nothing today (no rule targets that path) but it is exactly the kind of
thing that is discovered during an incident rather than a config review. Options,
cheapest first:

1. **Document it** in `geo_rules.yml`'s comments and in the fahrengit-451 README:
   static paths need their guard inlined, not a separate location.
2. **Inline the guard when a rule is added** — the `$geoblock_*` variables are
   computed at `http{}` level in `repo_vars.conf`, so `if ($geoblock_fdroid) { … }`
   works inside the static location. It cannot be added *unconditionally*, though:
   referencing an undefined nginx variable is a config-load error, so the guard
   only compiles once a rule for that path exists.
3. **Teach the watcher about static paths** — emit the guard as an includable
   per-path snippet (empty when no rule applies) that a static location can
   `include` unconditionally. This is the clean fix and a small one, but it is
   feature work on fahrengit-451 and is not needed until geofencing is actually
   wanted.

Recommend 1 now, 3 if and when a rule is added.

## 6. Disk and ops

~112 MB per published version set; with `archive_older: 3`, ~450 MB steady-state
in the `fdroid_repo` volume. Worth confirming the droplet's free space — this is a
VPS also holding `forgejo_data` with every release asset ever published (~125 MB
per release), so the two grow together.

Everything in the volume is regenerable from the Forgejo releases **except the
index signing keystore** — that is the one thing to back up off-box, and losing it
means every device re-adds the repo. Nothing else is stateful except the
last-published-tag marker, which is self-healing.

Operationally the service inherits the stack's existing conventions:
`restart: unless-stopped`, logs via `docker compose logs fdroid`, and
`docker compose restart fdroid` to force a republish. No host packages, no systemd
units, no distro assumptions about the droplet.

## 8. Effort delta vs. option A

C2 is roughly **+2 h** over A — and it deletes work from the shepherd-launcher
side rather than adding it, because `release.yml` is untouched:

| | A | C1 (ssh push) | C2 (compose service) |
|---|---|---|---|
| nginx location + volume (fahrengit-451) | — | ~1 h | ~1 h |
| deploy credential + `rrsync` lockdown + SSH ingress | — | ~1 h + a policy decision | — |
| `release.yml` job + APK re-download | ~1 h | ~1 h | — |
| sync service + Dockerfile + compose wiring | — | — | ~3 h |
| icons / screenshots / archive / landing page | n/a | ~2 h | ~2 h |

The split of the work also changes shape, which is worth naming because it
affects who reviews what:

- **fahrengit-451** — the `fdroid` service (Dockerfile + sync loop), the
  `fdroid_repo` volume, the nginx `location` + cache `map`, `config/fdroid.yml`,
  and a README section. This is where all the new machinery lives.
- **shepherd-launcher** — `dist/fdroid/config.yml` + two metadata files,
  `shepherd package fdroid` for local testing against a throwaway keystore, and
  the `INSTALL.md`/README docs. **No `release.yml` change, no new CI secret, no
  new CI image layer.**

Which means §4 of the main design (the `release.yml` job and its
cross-job-artifact workaround) and §3 (`publish-fdroid.sh`) drop out entirely
under C2; §1 (metadata) and §5 (docs) stay as written, and §2 becomes a
local-testing convenience rather than the thing CI runs.

## 9. What shepherd-launcher itself has to implement

Strictly: **nothing is blocking.** `fdroid update -c` generates stub metadata from
the APKs, so the compose service could publish a working repo with no change to
this repo at all. But three things belong here, and one of them is a security
control rather than a nicety.

### 9.1 `dist/fdroid/metadata/<appid>.yml` × 2 — and `AllowedAPKSigningKeys`

Ordinary fields (`Categories`, `License`, `AuthorName`, `WebSite`, `SourceCode`,
`IssueTracker`, `Summary` ≤ 80 chars, `Description` ≤ 4000, `ArchivePolicy`) are
just listing quality. The field that earns its keep is:

```yaml
AllowedAPKSigningKeys: b96abc13004bb75dd4caa412714035e9ce172bf4cb125ea1228163f68636041e
```

`fdroid update` refuses to publish any APK not signed by a pinned certificate, and
deletes it outright under `--delete-unknown`. Under C2 the droplet pulls release
assets **with no human in the loop**, so this is what stops a release asset signed
with anything other than the project key from reaching the repo and being
installed as an in-place upgrade on a family device.

Verified against the live v0.3.0 assets — both APKs carry exactly one signer, and
it is the same one:

```
Signer #1 certificate DN:  CN=Shepherd Launcher, O=armeafamily, C=US
Signer #1 SHA-256 digest:  b96abc13004bb75dd4caa412714035e9ce172bf4cb125ea1228163f68636041e
Verified using v2 scheme (APK Signature Scheme v2): true    (v1 false, v3 false)
```

So one pinned value covers both apps. v2-only is correct and sufficient here:
`fdroidserver` verifies via `apksigner`, and v1 is unnecessary because both
modules set `minSdk` ≥ 24.

This is also the argument for metadata living in *this* repo rather than in
fahrengit-451: it is a versioned, reviewable assertion about this project's
release key, and it should move through the same review as the code it protects.

### 9.2 `shepherd package fdroid` — local generation

Sibling to `shepherd package deb`: take `dist/pkg/*.apk`, stage `repo/`,
materialise `config.yml`, generate against a throwaway keystore, leave a servable
tree. Two jobs — iterate on descriptions and screenshots without pushing a tag,
and give CI something to run (9.3).

### 9.3 A CI check — the one thing C2 actually *needs* from this repo

C2's failure mode is that a malformed metadata file is discovered by a container
on the droplet, fifteen minutes after a tag, where nobody is looking. Closing that
gap is cheap, in two tiers:

- **PR-time, cheap:** a metadata syntax/lint check (`fdroid readmeta` or plain
  yamllint over `dist/fdroid/metadata/`). Note that neither existing CI job can do
  better than this — `android-companion` runs unit tests and `android-media`
  builds only the cdylib, so no APK exists at PR time, and a debug APK would be
  rejected by `AllowedAPKSigningKeys` anyway.
- **Release-time, complete:** run `shepherd package fdroid` as a step in
  `release.yml`'s existing `apk` job, which *does* have a signed release APK in
  hand. That exercises the real `fdroid update` — including the signing-key pin —
  before the droplet ever sees the tag. It publishes nothing; it is a dry run that
  fails the release if the repo wouldn't build.

The second is the valuable one, and it is the only `release.yml` change under C2 —
a validation step, not a publish step.

### 9.4 Docs

`docs/INSTALL.md` gets the "Installing the Android apps from F-Droid" section
(repo URL + fingerprint + QR, which devices self-update, `adb install` retained as
the Fire TV path); `companion-android/README.md` and
`crates/shepherd-media-android/README.md` get a pointer each.

### 9.5 Explicitly nothing

Worth recording so nobody goes looking:

- **No Gradle changes.** Stable `applicationId`, monotonic `versionCode`, and a
  v2 signature are all already in place — the apps are F-Droid-ready as built.
- **No new CI secret and no CI image change** (the release-time check needs
  `fdroidserver` in the android image; the PR-time lint does not).
- **No `shepherd version check` entry.** `fdroid update` reads `versionCode` and
  `versionName` out of the APK, so `VERSION` stays the single source of truth and
  there is no new literal to keep in harmony. Keep metadata version-free.

### 9.6 Optional, later

Screenshots and localized descriptions. `fdroidserver` accepts localized graphics
either next to the metadata or under `repo/<appid>/<locale>/` — confirm which at
implementation time. The captures in `docs/readme/` are launcher shots, so
companion/media screenshots would need capturing on-device; the adb workflow from
the BLE on-device testing notes already covers that (`adb exec-out screencap`).
