# Signing releases, on GitHub (#203)

## Prompt

> we'll need to do #203 first — sketch that out now that we're truly on GitHub

A sketch, not an implementation. It follows
[`2026-09-19 005 self-hosted-apt-repo (#204).md`](2026-09-19%20005%20self-hosted-apt-repo%20(%23204).md),
which settled where packages will be published, and which makes the
repository-metadata half of #203 ours to do rather than a platform's.

## What changed since the issue was written

#203 was written while the release was leaving Forgejo, and it listed three
open questions: repository-metadata signing, signing the `.deb` itself, and
where the key lives. Two of the three now have better answers than they did:

* **Metadata signing is no longer free.** Forgejo auto-provisioned a key and
  signed the index; a Launchpad PPA would have too. Note 005 chose a
  self-hosted repository on Cloudflare Pages, so **we sign `InRelease`
  ourselves, with a key we own.** That is not optional — apt will not use a
  repository whose index it cannot verify — so the key exists no matter what
  else is decided here.
* **Being on GitHub adds a second, keyless option for the artifact.** GitHub
  [artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations)
  are available in public repositories on all plans, signed through the
  public-good Sigstore instance with a short-lived certificate, and verified
  with `gh attestation verify`. No key material exists to steal or rotate, and
  the attestation says more than a signature does: it binds the artifact's
  digest to this repository, this workflow, and this commit.
* **`dpkg-sig`, which the issue names, is gone.** It is not in the Ubuntu 26.04
  archive (checked: `apt-cache policy dpkg-sig` finds nothing; `debsigs` and
  `debsig-verify` are there, in universe). And nothing verifies a `debsigs`
  signature by default — `dpkg` checks one only when an operator has installed
  a policy under `/etc/debsig/policies/<fingerprint>/`. In-`.deb` signatures
  are a dead end; a detached signature beside the asset is not.

## The two paths, which are independent

A package reaches a device by one of two routes, and they need different
things:

| Route | What protects it today | What it needs |
|---|---|---|
| `apt install lunchbox` from the repository | nothing (Forgejo's key is going away) | a signed `InRelease`; apt then checks each `.deb` against the SHA256 in the signed index |
| Download the `.deb` from GitHub Releases | a `.sha256` sidecar — integrity, not authenticity | a signature, or a provenance attestation, or both |

The apt route needs exactly one thing and has no alternatives. The download
route is where the choice lives.

## Path A — the repository key (required)

**Shape.** An Ed25519 primary key kept offline, with an Ed25519 *signing
subkey* exported for CI. `gpg --export-secret-subkeys` gives CI the ability to
sign and nothing else: it cannot certify, cannot add subkeys, and cannot revoke
— so recovering from a CI compromise stays possible from the offline primary,
which never touches a runner.

Ed25519 rather than RSA because it is smaller and every target client is Ubuntu
26.04 or newer. Verified rather than assumed: the note-005 probe was re-run end
to end with an Ed25519 key, and `apt-get update` accepted the `InRelease` and
installed from the index exactly as it did with RSA-3072.

**Where it lives.** A repository secret, base64-armoured, following the pattern
the Android keystore already set (`LUNCHBOX_KEYSTORE_B64` +
`LUNCHBOX_KEYSTORE_PASSWORD`):

```
LUNCHBOX_APT_KEY_B64          base64 of the armoured secret *subkey* export
LUNCHBOX_APT_KEY_PASSPHRASE   passphrase for it
```

Scoped to a **GitHub Environment** (`release`) rather than to the repository at
large, so only the publish job can read it, and — the choice taken below — so a
required reviewer puts a human in front of every signature. That gating is the
part that is new on GitHub; Forgejo had no equivalent.

**What it signs.** `dists/stable/Release` → `InRelease` (clearsigned) and
`Release.gpg` (detached), in the same publish job that generates the index (see
note 005). Nothing else on this path: apt derives the `.deb`'s authenticity
from the signed index.

**How the public half is published.** Two places, and they must agree:
`repository.key` at the site root — the URL `docs/INSTALL.md` already tells
people to fetch — and a copy committed in the repo (e.g.
`dist/apt/repository.key`), which is what the publish job deploys. Committing
it means the key that users trust is reviewable in `git log` and changes to it
show up in a diff, instead of appearing silently in a deployment.

**Expiry is the operational trap.** An expired signing key does not degrade,
it stops every `apt update` on every installed device with a hard error, and
the fix requires each device to fetch a new `repository.key` — over a channel
apt can no longer use. Options, in the order they get less risky and more work:

1. *No expiry on either key.* Simplest, and what many third-party repositories
   do. Rotation then happens only on compromise, which is the case that needs
   manual intervention anyway.
2. *No expiry on the primary, a dated signing subkey* (2–3 years), with a
   calendar reminder and a renewal that re-exports the subkey secret and
   republishes `repository.key`. Safer in theory; the renewal still has to
   reach devices before the old subkey expires.
3. *Ship the keyring in the `lunchbox` package itself*, so `apt upgrade`
   refreshes it while the current key is still valid. Worth knowing what this
   does and does not buy: it is a **rotation** mechanism, not a bootstrap one
   — a fresh install still needs the key before apt can fetch anything. It also
   brushes against an existing boundary: `scripts/lib/migrate.sh` states that
   `/etc/apt/sources.list.d/*.list` is the operator's file, "written by the
   operator following docs/INSTALL.md, not by `install`". Shipping a keyring
   under `/usr/share/keyrings/` does not cross that line; shipping the sources
   list would.

Chosen: **(1)**, no expiry. See Decisions.

## Path B — the downloaded `.deb`

Two complementary controls, neither of which needs anything the repository key
does not already provide:

**A detached `.asc` beside each release asset**, made with the same signing
subkey, alongside the existing `.sha256`. Verification is `gpg --verify
lunchbox_X.Y.Z_amd64.deb.asc lunchbox_X.Y.Z_amd64.deb` against the same
`repository.key` the apt instructions already install — one key, one trust
decision, two paths covered.

**A build-provenance attestation** via `actions/attest-build-provenance`,
verified with:

```
gh attestation verify lunchbox_0.5.1_amd64.deb -R aarmea/lunchbox
```

It needs `id-token: write` and `attestations: write` on the job, costs no key
management at all, and answers a question the signature cannot: *which workflow
run, from which commit, produced this file.* A signature says "the key holder
released this"; the attestation says "this came out of `release.yml` at tag
`v0.5.1`". For a package whose `postinst` runs as root, that is the more useful
claim of the two.

Keep the `.sha256` sidecars. They are not authenticity, but they are what a
scripted download checks cheaply.

## The chain, end to end

```
tag v0.5.1
  └── release.yml (environment: release, required reviewer)
        ├── .deb built per arch
        │     ├── .sha256                integrity
        │     ├── .asc                   signed by the offline-issued subkey
        │     └── attestation            Sigstore, binds digest→repo→workflow→commit
        ├── assets uploaded to the GitHub release        ← must happen first
        └── apt index generated, InRelease signed, deployed to Pages
              └── Packages carries each .deb's SHA256 ───┘ apt's integrity link
```

## What each control does not cover

Worth being plain about, because signing invites over-claiming:

* The release job holds both the signing subkey and the Cloudflare token, so a
  compromise of that job can produce a signed index *and* publish it. The
  environment gate and the offline primary limit the blast radius and make
  recovery possible; they do not make that scenario impossible. Signing
  off-CI from a workstation is the only arrangement that would, and it costs
  an automated release.
* The attestation proves provenance, not correctness: it says the artifact came
  from this repository's workflow, not that the commit it was built from is
  trustworthy.
* Nothing here protects a device that already trusts a compromised key. Key
  revocation reaches devices only through an `apt upgrade` that still verifies,
  which is the argument for option (3) above.

## Decisions

All settled in the session that produced this note:

1. **Identity:** `Lunchbox Archive Signing Key <apt@lunchbox-os.com>` — the
   project, not the maintainer, tied to the domain that serves the repository.
   The address does not need to receive mail; it needs to be one we control,
   which the zone already is.
2. **Expiry: none**, on primary or subkey. An expired signing key does not
   degrade, it stops every `apt update` on every installed device at once and
   the fix cannot travel over apt. Rotation therefore happens only on
   compromise, which needs manual intervention regardless. Revisit if the
   repository ever gains a second publisher.
3. **Custody: the password manager**, alongside the Android release keystore
   and the rest of the release key material, which is already where they live.
   Stored there: the armoured primary export, its passphrase and the
   **revocation certificate** — generate that at the same time as the key, not
   at the time it is needed.
4. **CI gate: a `release` environment with a required reviewer.** The two
   secrets are readable only by the publish job, and a pushed tag waits for a
   human before anything is signed or deployed.
5. **Artifact: both.** A `.asc` sidecar signed with the same subkey, and a
   Sigstore build-provenance attestation. They answer different questions and
   need different tools, and neither costs anything the other already pays.
6. **`repository.key` is committed** at `dist/apt/repository.key` as well as
   deployed, so a change to what users trust shows up in a diff.

## Sequencing

1. Generate the key and its revocation certificate; export the signing subkey;
   add the two secrets and the `release` environment; commit
   `dist/apt/repository.key`. Written up as a runbook with exact commands in
   [`docs/release-signing.md`](../../release-signing.md) — every `gpg`
   invocation there was run in a scratch keyring first, and the
   `sec#`/`ssb` check and the `gpgv` verification are that run's real output.
2. Implement note 005's `publish-apt.sh` and its job, which signs the index as
   its last step — at which point the apt path is live and #204 is closed by
   the self-hosted repository rather than a PPA.
3. Add `.asc` + attestation to the release build jobs, and the two verification
   recipes to `docs/INSTALL.md`.
