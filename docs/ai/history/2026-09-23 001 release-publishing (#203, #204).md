# Building the release and apt publishing (#203, #204)

## Prompt

> `/remote-control` — #223 is checked out. let's pick up where it left off

PR #223 had the three design commits (notes 004–006 and
`docs/release-signing.md`), green and unreviewed. Its "picking this up" list
was: the key ceremony (a human, with the password manager), then
`publish-apt.sh` and its job, then committing `repository.key`. Asked where the
implementation should go, the answer was **the same PR**, so #223 now carries
both the design and the build.

## What was wrong on arrival

The repository had been transferred to the **Lunchbox-OS** organization, and
the runbook still said `aarmea/lunchbox`. For most commands GitHub's redirect
hides that. For `gh attestation verify -R` it does not: the attestation records
the repository name at build time, so every release built after the transfer
would have failed verification against the old name. Fixed in this PR's docs
only. The rest of the tree (`CLAUDE.md`, `README.md`, `Cargo.toml`, …) still
says `aarmea/lunchbox`, which is a separate change.

## What was built

* **`scripts/ci/publish-apt.sh`**, rewritten from a Forgejo `PUT` into note
  005's static site: `dists/` signed, `repository.key`, and `_redirects` mapping
  `pool/<version>/<file>.deb` to the release asset. `--previous URL` appends to
  the published index after verifying `InRelease` against
  `dist/apt/repository.key` and each `Packages` against the SHA256 it signed.
  `--rebuild DIR` starts from nothing and requires a `.asc` that verifies for
  every `.deb` it indexes.
* **`scripts/ci/test-publish-apt.sh`** and the *apt repository* CI job. Offline:
  a throwaway key, synthetic `.deb`s, a Python server acting as Pages
  `_redirects`, and a real `apt-get` confined to the scratch tree. Twelve
  checks, including five refusals.
* **`sign-release-assets.sh`**, **`publish-release.sh`**,
  **`fetch-release-debs.sh`**, replacing the Forgejo `upload-release-asset.sh`.
* **`release.yml` re-enabled**, with the `publish` job ported: sign → attest →
  release → apt index → deploy → smoke test, in the `release` environment.

## Where it departs from notes 005 and 006

* **One job, not a `publish-apt` job after the release job.** Both need the
  key, and GitHub asks for approval once per job that names the environment.
* **The first publish needs no flag.** A 404 on the published `InRelease`
  means there is no index yet, so the job rebuilds. Any other fetch failure
  fails the step instead: a DNS or 5xx error must not quietly trigger a
  rebuild. A rebuild can also be asked for with the `apt_rebuild` dispatch
  input.
* **The tag in `_redirects` is derived, not recorded.** It is `v` + the pool
  directory's version. That relies on the guard, which already refuses a tag
  that is not `v$(VERSION)`. So `_redirects` is a pure function of `Packages`,
  and regenerating it with the current `github.repository` on every publish
  also absorbs a future repository move.
* **A rebuild verifies each `.asc`.** Everything it indexes is about to be
  signed into the index, so it has to be ours. That turned up a gap in note
  006's rotation procedure: after a rotation every past `.asc` is by the old
  key, so a rebuild refuses them all. The runbook now says to check each past
  `.deb` against its attestation, which no key of ours can forge, re-sign the
  `.asc` files, and then rebuild.
* **The public key must be named `.asc` for apt.** apt ignores an armoured key
  under `signed-by` unless the filename ends in `.asc`, calling it an
  "unsupported filetype". `docs/INSTALL.md` already names it
  `lunchbox-os.asc`. The test found this, and the smoke test in `release.yml`
  follows it.

## Checked, and not

Checked here: the whole apt path through `test-publish-apt.sh`;
`sign-release-assets.sh` against a throwaway key, including a wrong passphrase
with a fresh agent; the `gpgv` recipe in `docs/INSTALL.md` against a good file
and a tampered one; `release.yml` with actionlint (and the shellcheck it runs
over each `run:` block).

**Not run against GitHub or Cloudflare**, because nothing here can be without
a tag: `publish-release.sh`, `fetch-release-debs.sh`, the attestation step,
the environment gate, the Pages deploy and the live smoke test. The first
release is their first run. Two specific uncertainties:

* whether `apt.lunchbox-os.com` answers **404** before the first deployment,
  which the automatic first-publish rebuild depends on. If it answers anything
  else, dispatch with `apt_rebuild`.
* whether `actions/setup-node@v4` and `actions/attest-build-provenance@v4` behave
  as their docs say on this runner. Both are used in the ordinary way.
