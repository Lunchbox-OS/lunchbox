# Joining WEP networks, and keeping the keyboard out of password fields (#194)

Two pieces of follow-up on PR #218, both from the maintainer testing the
companion on a phone.

## Password fields

**Prompt:** "in testing, I'm noticing that while the password is mostly
obscured, the IME is still providing suggestions which can both reveal parts of
the password and cause it to be autocorrected incorrectly. A reveal "eye" would
also be useful"

`PasswordVisualTransformation` only changes what Compose draws. None of the
four secret fields (the two Wi-Fi dialogs, the two web-password fields) set
`KeyboardType.Password`, so Gboard saw ordinary text. All four now go through
`ui/components/PasswordField.kt`, which sets it, turns autocorrect off, and
carries the show/hide eye. Revealing changes the transformation only; the
keyboard type stays `Password`. Built and installed on the Pixel, but not seen
on the phone: reaching the Wi-Fi dialog needs a paired device, and see
"Pairing" below.

## WEP

**Prompt:** "what's the justification for not allowing connections to WEP
networks? I get that they are cryptographically broken, but I fail to see how
connecting to one knowingly is any different from using an open network",
then, after the answer below, "add WEP support to this PR".

### There was no justification

The scope note listed "WEP." among the non-goals with no reason. The open
questions put to the maintainer asked only about Enterprise. The
implementation note then said Enterprise *and* WEP were left out "per the
maintainer's answer" — attributing the WEP half to a decision nobody made. It
now carries a correction.

On the merits the maintainer's point holds. Joining WEP knowingly is no worse
than an open network, which these UIs already join; Lunchbox's own traffic
does not rely on the link (TLS plus a password for the web, BLE for the
companion). Where WEP survives is exactly this project's audience: the
Nintendo DS joins only open or WEP networks, so a household with children may
keep an old WEP network alive, and it may be the one within reach of the TV.

### What NetworkManager does with a WEP key (measured, 1.54.3)

`nmcli --offline connection add` builds and validates a profile without
touching the running configuration, which is what made this safe to measure on
the dev box:

* A WEP profile is `key-mgmt=none`, `wep-key0`, `wep-key-type`.
* **`key-mgmt=none` with no key is also accepted**, and means an open network.
  So `key-mgmt` alone cannot tell WEP from open.
* `nmcli` guesses `wep-key-type` from the key: 5 or 13 characters, or 10 or 26
  hex digits, is `1` (the raw key); anything else is `2` (a passphrase).
  Measured on `abcde`, `0123456789`, `abcdefghijklm`, a 26-digit hex key
  (all 1), and `abcdef`, `letmein-ok` (both 2). `correct-horse` — 13
  characters — is guessed as a key, not a passphrase.
* The dev box's wpa_supplicant (2.11) is built with WEP, and its adapter
  reports both WEP ciphers (`WirelessCapabilities` 1919).

### What changed

1. **The saved-network reader** mapped `key-mgmt=none` to Open, so any WEP
   profile — including one GNOME wrote — was listed as open. It now reads
   `none` plus any `wep-*` property as WEP. `GetSettings` withholds the key
   but returns `wep-key-type`.
2. **Validation and the custodian.** A WEP key is any of the four raw-key
   shapes or a 1–64 character printable passphrase. The profile gets
   `wep-key-type` guessed the way `nmcli` guesses, and `wep-key-flags = 0` for
   the same reason as `psk-flags` (no secret agent in the kiosk).
3. **Both UIs** offer WEP in the picker and the manual form, show the forms a
   key may take under the field, and say for WEP only that the network is as
   readable as an open one. Joining knowingly is the justification; the note is
   where the knowing comes from.

   Asked next whether open networks got the same warning: they did not, which
   left WEP warned about by comparison with a network joined silently. Both
   now say anyone nearby can read the traffic; Enhanced Open says nothing,
   since it is encrypted.

Left to admin mode: shared-key authentication, a key in a slot other than the
first, and a 5- or 13-character passphrase (taken as a raw key, as `nmcli`
takes it). Enterprise stays out, as decided.

### Not verified

* **No join against a real WEP network.** There is none on the bench, and
  `hostapd` is not installed for the hwsim approach the scope note describes.
* **How a wrong WEP key is reported is expected, not measured.** In WEP's
  usual open-system mode association succeeds with any key and the failure
  shows up as DHCP never answering. NetworkManager's Wi-Fi device treats an IP
  timeout on a static-WEP profile as a probable wrong key and asks for new
  secrets, which with no agent should end in reason 7 (`no-secrets`) — so the
  UIs would say "wrong password", after the DHCP timeout rather than quickly.
  A genuine DHCP failure on a WEP network would then also read as a wrong
  password. That is from reading NetworkManager, not from a run.

## Pairing

Trying to reach the Wi-Fi dialog on the Pixel against the headless session
found that the dev box's current adapter (`28:18:78:45:B6:1E`, a Realtek combo
dongle) pairs by **LE legacy Passkey Entry** — the daemon logs `Passkey Entry
pairing requested … method="enter"` and the phone asks for the digits to be
typed — not Numeric Comparison. `companion-pairing`'s `pair.sh run` waits for
`Numeric Comparison pairing requested` and so cannot pair against this adapter.
A scratch variant that typed the passkey got through consent but did not find
the phone's entry dialog before the 30 s SMP timeout; not pursued further.
